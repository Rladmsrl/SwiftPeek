# iOS 小窗弹幕性能

本次处理的反馈是：直播和录像在系统小窗开启弹幕后低帧率，退到后台更明显。

## 查到的问题

- 合成由主线程 24 Hz Timer 驱动，逐帧构建多层 Core Image 图并同步渲染，会与界面操作争用主线程。
- 直播采样使用“距上一张保留帧至少 1/24 秒”，30 fps 输入因此隔帧取样，实际约为 15 fps；浮点间隔比较也会错误丢帧。
- 直播缩放持有取帧读锁，界面取帧可能等待缩放完成。
- 合成依赖应用 GPU 工作。Apple 明确说明 [iOS 会限制后台应用提交 Metal 工作](https://developer.apple.com/documentation/metal/preparing-your-metal-app-to-run-in-the-background)，因此该路径不适合依赖后台持续合成。
- 合成帧使用宿主时钟 PTS，但录像的 layer timebase 使用媒体时间，且同时设置 DisplayImmediately；AVFoundation 头文件明确不建议混用控制时基与立即显示附件。

以上是已确认的代码行为，尚未通过用户真机日志量化每项对实际卡顿的贡献。

## 改动

`PiPFramePump` 使用独立串行队列按 60 fps 目标推进弹幕动画，最多保留一份最新输入。主线程仅采集 UI 所有的数据与视频帧，采样最多 30 fps，最多一个待处理采集请求；UI 暂时繁忙时，工作队列仍可使用最近画面推进弹幕。迟到的工作不排队追赶，系统渲染器产生背压时跳过本帧。

视频缩放采用 vImage，缓存的文字位图直接绘制进 IOSurface 支持的像素缓冲，不依赖 Core Image/Metal 合成。直播保留缩小后的 480 像素长边视频，合成输出长边最多 960 像素；直播保留帧预算仍有 96 MiB 上限，输出池限制为 6 帧。

直播按固定采样时刻推进，最多保留 30 fps；不通过解码后的 GPU 缩放持有读锁。合成 PTS 与对应播放时基一致；暂停冻结弹幕，拖动/切源清理旧帧，关闭小窗拒绝迟到提交，重开时使用新 generation。

这只改变 iOS 小窗合成路径，不改变 macOS 原有的 Core Animation 浮窗弹幕路径。60 fps 是调度目标，系统实际显示帧率还受设备、负载和源视频影响。

## 验证（2026-10-23）

- iOS Debug 编译通过；直播与真实录像的画面内播放、弹幕开关、设置保存/重开 UI 回归通过。
- 离线检查覆盖真实 H.264 解码、24/25/30/50/60 fps 输入采样、实际合成像素、字幕方向、暂停/恢复、拖动清空、显隐和切源。
- 工作队列在没有新 UI 输入的 0.8 秒中输出 48 帧，且弹幕像素持续移动；背压、停止后的迟到帧、旧 generation 提交拒绝检查通过。
- 同一台 Mac 的离线压力用例（1080p 输入、360 次合成、舍弃前 60 次预热、峰值 69 条可见弹幕）：平均合成耗时由约 5.11 ms 降为 2.43 ms，P95 由约 7.91 ms 降为 3.06 ms。两次均无合成失败。这是合成耗时对比，不是真机 PiP FPS。
- Duo iOS 27.1 模拟器在测试进程和 App 上下文均报告系统 PiP 不受支持。该项明确跳过；没有用模拟浮窗冒充系统小窗。随后测试版已在 iOS 27.2 Duo 上安装，由维护者自测并确认可用；真实前后台 PiP 显示帧率尚未量化采集。

运行离线检查：先构建共享 macOS 库，再执行 `macos_native/Checks/check-pip-danmaku.sh <包含 SimpleLiveKit.o 的产物目录>`。

真机开启系统小窗弹幕后，每 5 秒记录一次本地 `pip.composite.stats`：`enqueuedFPS` 是提交帧率、`sourceFPS` 是新源帧变化频率、`meanRenderMS` 是合成平均耗时、`maxInputAgeMS` 是输入采样延迟、`dropped` 是背压/缓冲池导致的跳帧数。提交帧率不能直接当作系统实际呈现帧率。日志不包含弹幕正文、设备标识或播放地址，按仓库要求保留在本地。
