# SwiftPeek · macOS / iOS 关注分享

采用用户确认的“隔空投送、手动合并”方案。关注文件由两端共同识别，不需要账号、服务器或域名。
它是手动传递当前列表的快照，不会自动同步以后发生的变更，也不会同步删除操作。

## 使用

1. 两台设备都安装包含此功能的 SwiftPeek（原 Simple Live 原生版，文件格式从 0.4.1 起支持）。
2. 发送端打开“关注 / 我的关注”，点击“分享关注”，在系统分享面板选择“隔空投送”和目标设备。
3. 接收端接收 `SwiftPeek 关注.simplelivefollows`，用 SwiftPeek 打开，查看新增关注、已关注与历史更新数量，再点击“合并”。
4. 若系统将文件保存到“文件”或“下载”而未直接交给 App，在接收端的关注页点击“导入关注”，选择该文件。
5. 两边各有不同关注时，将合并后的列表再分享回原设备，即可得到相同的关注集合。

分享通过系统 [ShareLink](https://developer.apple.com/documentation/swiftui/sharelink) 发起，目标设备由用户自行选择。
开发期间未实际发送文件，未启动 UI 或操作用户设备。

## 合并规则

- 包含斗鱼关注的房间号、主播名称、房间标题与头像地址，以及观看历史（房间号、主播名称、标题、封面、观看时间）。
- 不包含设置、Cookie、账号、取流凭据或播放地址。
- 关注以房间号去重；本机已经关注的记录保持不变，仅加入缺少的记录。
- 历史以房间号合并：本机没有或文件中观看时间更晚的才写入，合并后按时间倒序并按“历史保留条数”裁剪。
  本机“记录观看历史”关闭时不导入历史。
- 文件格式版本：无历史时仍写 `version: 1`，与旧版兼容；带历史时写 `version: 2`，
  只认识版本 1 的旧版 App 会提示更新后再导入。
- 同一文件重复导入不重复添加。文件内部重复条目也会去重。
- 预览不会写入；点击合并时重新计算新增数量，避免预览期间本机列表变化造成重复。
- 先原子保存本机文件，再更新界面。保存失败不声称成功，也不修改内存中的列表。
- 未知版本、非法平台或房间号、非法头像 / 封面地址、超过 2 MB / 2,000 条关注或 2,000 条历史的输入会被拒绝。
- 分享副本仅在 App 的临时目录中生成，后续分享时清理该目录中超过 48 小时的副本。

## 文件与入口

- 扩展名：`.simplelivefollows`
- UTI：`com.simplelive.follows`，继承 `public.json`
- MIME：`application/vnd.simplelive.follows+json`
- 两端 `project.yml` 注册相同类型与 Viewer 文档入口；收到 file URL 后交给导入预览。
- “导入关注”同时允许选择 JSON 扩展名的同格式文件；不接受任意历史 Flutter 备份结构。
- 原有 `simplelive://room/...` 房间链接继续有效，文件导入不截获网络 URL 或直播间深链。

Universal Links 本轮未接入。它还需要部署域名对应的 AASA 文件并配置关联域名与签名能力，
详见 [Apple Associated Domains](https://developer.apple.com/documentation/xcode/supporting-associated-domains)。
当前选定的文件分享方案不依赖上述条件。

## 验证边界

- 核心库 30 项测试通过，包含文件往返、去重、历史按时间合并、新旧版本兼容、未知版本、畸形 / 超限输入与字段校验。
- `macos_native/Checks/check-follow-sharing.sh` 使用临时目录验证真实 LibraryStore 和导入控制器：
  文件读取与预览、合并与重载、保留本机元信息和历史、重复合并、反向合并、保存失败，
  以及历史按房间取最近一次、关闭历史时不导入、按保留条数裁剪。
- macOS / iOS Release 编译通过；检查生成的 Info.plist 中两端文档类型一致。
- 未在两台物理设备之间验证隔空投送可见性、实际文件分发或默认打开应用关联。
- iOS 本次产物未签名，也未安装到手机；需用户通过 Xcode 既有签名配置安装。
